# 歌词失败项排查与补跑

`0.8.5.2-preview.8` · Android `versionCode 140` · 本地 ARM64 测试版，未发布 Release。

## 本轮范围

通过原任务的重试入口补跑已有失败项，不重扫、不删除既有缓存或离线音频。任务身份和检查点在重试前后核对，详细现场材料不进入公开仓库。

## 已证实的问题

- 手机对 LRCLIB 的实际响应包含 `503 ServerOverloaded` 和 `Retry-After: 1`。同一时段已有缓存的请求可能成功，陌生曲目的查找仍可被拒绝；不能据此说整个站点完全宕机，也不能把这些错误记为无词。LRCLIB 当前官方文档要求串行、节流并遵守等待时间。
- 原代码未读取等待指令；精确查询确认 `instrumental: true` 后仍额外搜索，后续过载会把该结果变成失败。此纯音乐分支已用实际源码测试复现，不能据此推断全部历史失败都属于纯音乐。
- 超过接口时长范围的长录音可能收到 HTTP 400；duration 支持范围为 1–3600 秒。修复为省略接口不支持的可选参数，不伪造或夹取时长。
- 服务器空歌词响应可能耗时较长。140 将这类读取并入两请求配额，并从实际发出后给予有限的 30 秒等待；普通请求仍为 15 秒。旧失败未保存异常，不能把旧的普通失败全部归因为冷盘超时。

## 修改

NAS 歌词处理仍可推进多个任务，外部 LRCLIB 请求则共用一条独立队列。每次完整读取响应体后让出时间，开始间隔至少 700ms、结束后至少 250ms。429、500、502、503、504 只做最多 3 次尝试，尊重 Retry-After 秒数或 HTTP 日期并加正向随机错峰。排队和退避不占单次请求的 15 秒期限；跨任务共享冷却，后面的任务不能绕过服务器的等待指令。长等待保留为可重试错误，不提前发请求。

精确纯音乐响应不再追加搜索。服务器无词时，先检查该曲已下载的旁档或嵌词，再访问外部来源。非空而当前不支持的歌词格式保持为失败，不冒充无歌词。来源、账号、暂停及晚到响应的检查保留。

新增安全错误分类日志只包含曲目编号、白名单错误类型、状态和 bundle 数字位置；不记录错误消息、原始堆栈、URL、凭据或歌词正文。诊断失败不改变任务结果或失败预算。
